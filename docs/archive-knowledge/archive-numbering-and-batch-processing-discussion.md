# 档号与批量归档处理讨论纪要

本文记录 2026-07-30 围绕档号生命周期、预归档与室藏录入、原子批处理和容错批量处理形成的候选理解。它用于延续设计讨论，不是当前业务合同；决定实施后，仍需将选定要求写入对应 OpenSpec。

## 讨论结论

1. 档案 ID 是系统内部稳定身份，档号是正式档案的业务识别代码，实物条码和库位编码分别承担实物识别与位置表达，四者不得混用。
2. 正式档号一旦成功提交便永久占用。档案删除、作废、移交或改号后，旧档号均不得重新分配。
3. 预归档库不应在数据进入时立即生成正式档号。预归档记录使用接收编号；用户填写的既有档号先作为申报档号，完成归档时再校验并正式定号。
4. 室藏库默认只管理已经整理、校验和定号的正式档案，不作为普通数据录入区；少量历史档案补录可以通过受控的“直接归档”形成室藏档案。
5. 项目讨论中约定：`Batch` 表示任一失败整批回滚的原子批处理；`Bulk` 表示允许部分成功，并可选择遇错继续或遇错停止的容错批量处理。
6. Batch 和 Bulk 都不得绕过单条权限、数据范围、运行时约束、字段校验、档号唯一性和审计。

## 档号相关身份

| 概念 | 建议字段 | 含义 | 是否占用正式档号 |
| --- | --- | --- | --- |
| 档案 ID | `archiveId` | 系统内部永久身份，供关联和技术定位使用 | 否 |
| 接收编号 | `intakeNo` | 标识一次预归档接收记录或暂存记录 | 否 |
| 申报档号 | `declaredArchiveNo` | 用户或外部数据提供、尚待核验的既有档号 | 否 |
| 正式档号 | `archiveNo` | 完成定号并成功提交后的正式业务识别代码 | 是 |
| 实物条码 | `barcode` | 标识实物对象 | 否 |
| 库位编码 | `locationCode` | 标识实物当前存放位置 | 否 |

“申报档号”不是软占号。两个预归档记录可能申报相同档号，系统可以提前提示冲突，但必须在正式定号事务中重新校验，最终只能有一个成功提交。如果业务要求填写后立即保证号码归属，该动作已经属于正式定号或预留号段，需要承担号码不可复用的后果。

## 档号生命周期

```text
进入预归档库
  │
  ├─ 生成接收编号
  ├─ 清洗、分类、组卷和补充元数据
  ├─ 可填写申报档号
  └─ 可预览预计档号，但不推进计数器
          │
          ▼
       完成归档
          │
          ├─ 最终校验
          ├─ 手工定号或自动定号
          ├─ 写入档号分配记录和审计
          └─ 进入室藏库
```

正式档号的建议状态只有“未分配”和“已分配”。预览结果不成为持久化状态，也不对并发请求构成承诺。

### 自动定号

自动定号根据已发布编号规则和最终业务数据生成档号。分类、年度、保管期限、机构或问题、项目、案卷归属等会影响档号的字段，应在定号前确定。

如果件级档号包含案卷号，已经定号的条目不能通过普通操作移动到其他案卷。确需移动时，应执行受控改号并保留旧号历史。

### 用户填写档号

用户填写档号分为三种语义：

| 场景 | 处理方式 |
| --- | --- |
| 预归档阶段填写 | 保存为申报档号；允许修改；不占号 |
| 直接创建正式室藏档案 | 作为手工定号；校验通过并提交后永久占号 |
| 已有正式档号后修改 | 使用档号更正动作；普通档案编辑不得直接修改 |

新形成档案的手工档号应符合当前编号规则。历史档案导入可以保留不符合现行规则的旧档号，但应标记来源、填写原因并经过更高权限确认。

如果手工档号能解析出当前编号作用域内的流水号，正式定号时应原子抬高计数器水位，避免后续自动定号反复撞号；不能解析的历史档号只参与全历史唯一性校验。

### 改号、删除和作废

改号必须记录旧档号、新档号、原因、操作人和操作时间。新档号成为当前档号，旧档号继续作为已经使用过的档号保留。

以下情况均不得释放正式档号：

- 档案逻辑删除或恢复；
- 档案业务作废；
- 档案从室藏库移至其他业务库；
- 档案完成档号更正；
- 已经正式定号后未能继续后续业务流程。

只有从未提交成功的事务内候选号才可以重新使用。

## 预归档与室藏录入

正常业务路径为：

```text
录入或导入
    ↓
预归档
    ↓ 整理、校验、组卷和定号
完成归档
    ↓
室藏
```

室藏库不提供无约束的普通新增。少量历史档案补录、纸质档案补建目录或管理员修复遗漏记录时，可以提供受控的“直接归档”，但服务端仍须一次性完成权限、字段、档号、数据范围和审计校验，并将正式档案写入与定号放在同一事务。

批量导入、外部系统接入和存量迁移原则上进入预归档流程，不通过直接归档绕过批次校验。

## Batch 与 Bulk

本讨论采用以下项目内术语，不主张它们是行业通用定义。

### Batch：原子批处理

Batch 将整批数据视为一个结果边界：

- 每条数据分别执行完整业务校验；
- 尽可能在写入前收集全部可发现的行级错误；
- 全部通过后进入一个写事务；
- 任一写入失败，档案、档号、动态字段、关系和审计全部回滚；
- 成功响应只表达整批成功，不产生部分成功状态。

Batch 适用于正式归档包接收和其他要求整批一致的业务。

### Bulk：容错批量处理

Bulk 将每条数据视为独立事务，允许部分成功，并支持：

| 失败策略 | 语义 |
| --- | --- |
| `CONTINUE_ON_ERROR` | 当前条失败并回滚，继续处理后续条目 |
| `STOP_ON_ERROR` | 当前条失败并回滚，保留此前成功结果，后续条目不再执行 |

单条结果状态建议区分：

- `SUCCEEDED`：已经成功提交；
- `FAILED`：已经尝试但失败；
- `NOT_ATTEMPTED`：因停止策略而未执行。

`STOP_ON_ERROR` 不是整批回滚。失败发生前已经提交的数据保持成功。Bulk 适用于存量补录、批量修复和后台迁移等允许部分成功的场景。

### 共享的单条业务核心

Batch 与 Bulk 应复用同一个单条准备能力，避免权限、数据范围、运行时约束、字段转换和编号规则分叉：

```text
               单条准备与校验
                       │
        ┌──────────────┴──────────────┐
        ▼                             ▼
Batch：全部准备后统一事务写入    Bulk：逐条事务写入
任一失败全部回滚                按失败策略继续或停止
```

批次执行上下文只应作为批处理模块内部的有类型执行计划存在，不应成为允许任意 Service 登记延迟 SQL 或副作用的通用作用域。

## Batch 的事务内取号

如果正式档号使用 PostgreSQL `sequence` 或在独立事务中预留，批次回滚后号码不会恢复，会留下断号。若业务要求 Batch 回滚后候选号恢复可用，应使用事务型计数器表，并让计数器推进、档号分配记录、档案写入和审计加入同一个事务。

```text
完成全部无副作用校验
        ↓
开启 Batch 事务
        ↓
执行不依赖档号的准备写入
        ↓
在事务尾部锁定编号计数器
        ↓
一次分配号段并批量写入档号
        ↓
立即提交；任一失败则连同计数器一起回滚
```

事务内计算但尚未提交的值是候选号，不是正式档号。Batch 回滚后重新使用候选号，不违反正式档号不得复用的原则。

## 并发取号

同一编号作用域使用行锁或原子计数器更新后，并发取号产生锁等待而不是重号：

```text
Batch 锁定计数器并取得 101—110
        │
单条操作尝试取号
        └─ 等待 Batch 结束

Batch 提交 → 单条取得 111
Batch 回滚 → 单条取得 101
```

为降低在线单条操作的等待：

1. 所有耗时校验和可提前完成的工作放在取号前；
2. Batch 在事务尾部取号，取号后只执行必要写入并立即提交；
3. 同一批次涉及多个编号作用域时，按稳定顺序锁定计数器，避免死锁；
4. 限制原子 Batch 的规模，超大数据集改用异步 Bulk；
5. 档号全历史唯一约束仍是并发条件下的最终数据库边界。

无法同时获得“号码可随事务回滚”“同一作用域完全无等待”和“永不产生断号”三个目标：

| 方案 | 回滚后候选号可用 | 同一作用域等待 | 可能断号 |
| --- | --- | --- | --- |
| Batch 事务内计数器 | 是 | 有 | 否 |
| 独立事务预留号段 | 否 | 很短 | 是 |
| PostgreSQL `sequence` | 否 | 很少 | 是 |

对于 Batch，候选号可回滚优先；对于吞吐量优先的 Bulk，可以按单条短事务取号，或者预留号段并接受未使用号码作废。

## 尚未形成实现合同的问题

- 档号全历史唯一性的最终机构作用域；
- 编号规则的具体组成项、版本状态和发布流程；
- 是否允许预留号段以及预留后的作废规则；
- Batch 的最大记录数、事务超时和锁等待上限；
- Bulk 采用同步响应还是异步任务，以及结果保留期限；
- 直接归档权限、审批要求和允许使用的业务场景；
- 当前已有档号数据迁移到全历史唯一记录时的冲突处理方式。

这些问题只有进入对应 OpenSpec 并形成可测试场景后，才构成实现要求。
