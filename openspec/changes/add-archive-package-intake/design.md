## Context

当前归档接收模块只有概览接口和占位页面；档案核心已经具备全宗、分类、数据范围、档案条目创建和系统库角色。repository role 是档案条目生命周期的唯一真相源：`INTAKE` 表示预归档、`HOLDING` 表示正式档案、`TRANSFER` 表示移交。归档接收需要新增独立的包级业务记录、检测和交接状态，并在确认接收后通过档案核心公开 Service 直接向 `HOLDING` 生成正式档案，不能绕过其权限、运行时规则和动态表写入边界。

该闭环面向人工离线交接的中小型档案信息包。格式基线采用截至 2026-07-29 仍现行的 DA/T 93—2022，四性检测项采用 DA/T 70—2018；GB/T 18894—2016、DA/T 46—2009 及各门类元数据标准继续作为内容格式和元数据方案的上位约束。信息包处理在一个 HTTP 请求内同步完成，但原包与接收记录、解析摘要和包处理分别使用清晰事务：原包与接收记录先提交，结构与自动检测通过后保存检测报告，条目与电子文件在一个处理事务内整体成功或整体回滚，失败状态再由独立事务保存。

## Goals / Non-Goals

**Goals:**

- 明确“移交信息包”“检测与交接记录”和“入库电子档案”是不同生命周期对象。
- 以 repository role 唯一表达档案条目处于预归档、正式保管或移交阶段，不再维护平行的电子状态。
- 支持 DA/T 93—2022 附录 B“件”级目录树的 ZIP 上传、原包留存、安全解析、自动四性检测、包内条目全量校验和原子生成。
- 自动检测通过后等待人工/外部复核；确认交接后将档案目录下的内容数据保存为正式档案电子文件，并允许接收人下载原始信息包核验。
- 任一处理失败时保留可追溯的失败记录、摘要和可理解原因，不留下部分条目。
- 提供当前用户的接收历史、详情和生成条目关联，并在 PC 工作台展示完整状态。

**Non-Goals:**

- 不支持 DA/T 48—2009 EEP 封装包和长期保存 AIP；不在缺少可信证书链、杀毒引擎或物理载体的情况下伪造电子签名、病毒、载体外观和读取速度检测结果。
- 不增加外部连接、后台任务、自动重试或通用审批流；本变更只实现接收人明确确认后的正式入库。
- 不允许查看其他用户的接收记录；跨人员接收监管后续另行设计。

## Decisions

### 1. 使用 DA/T 93—2022 附录 B“件”级信息包配置

网页接收 ZIP 是传输封装，不是标准自定义内容。ZIP 内可以直接放置信息包根内容，也可以只有一个顶层“电子档案移交信息包”目录。规范化后的根目录包含：

```text
电子档案移交信息包/
├── 说明文件.TXT
├── 目录文件.XML
├── 其他/                         # 可选，保存清单、登记表、规则等
└── F001/                         # 全宗文件夹，以系统全宗编码命名
    └── WS/                       # 项目映射：第一层分类目录使用系统分类编码
        └── .../                  # 可选的后续分类层次
            └── WS-2026-001/      # 电子档案文件夹，以档号命名
                ├── 电子档案1元数据.XML
                ├── 正文.pdf
                └── 附件1.ofd
```

`说明文件.TXT` 使用 GB18030、GB2312 或 UTF-8，至少可识别移交单位、内容描述、起止档号、档案数量、软硬件环境；离线载体参数、载体编号、载体数量、制作单位和检查单位缺失时记录警告。载体编号作为可选业务包编码，系统始终以接收记录 ID 和原包 SHA-256 保持唯一追踪。

`目录文件.XML` 只允许 GB18030、GB2312 或 UTF-8，根元素为 `文件目录`，每个 `文件` 至少提供顺序号、档号、责任者、题名、日期、保管期限、密级和备注；页数按 DA/T 93—2022 第 5.3.2 条检测，因附录 B 示例未列出该元素，缺失时记录警告而非拒绝。档号必须唯一，并与唯一的电子档案文件夹同名。电子档案文件夹至少包含一个可安全解析的元数据 XML 和一个内容文件。第一层分类目录采用系统分类编码是本项目与标准“按分类层次组织文件夹”之间的明确映射约定，不宣称是国家标准固定命名。

服务端限制上传压缩数据不超过 50 MiB、说明文件和目录文件各不超过 2 MiB、条目数 1–100、内容文件数不超过 500、单个文件不超过 50 MiB、解压总量不超过 200 MiB、ZIP 条目不超过 1000。拒绝加密条目、非公开压缩算法、绝对路径、反斜杠、`.`/`..` 路径、重复路径、非法根文件、缺失标准文件、非法 XML、DTD/外部实体、档号与文件夹不一致、未归属文件及数量不一致。解析器将文件流式写入随机命名临时文件，不按 ZIP 路径在文件系统展开，处理完成后统一清理。

本期只实现 DA/T 93—2022 给出的目录树方式。该标准同时允许按 DA/T 48—2009 组织 EEP；EEP 是独立格式配置，不能与本配置混合猜测解析。

### 2. 包记录使用固定实体，关联表记录生成结果

新增 `am_archive_intake_package` 固定表保存格式配置、包编码、原文件名、大小、SHA-256、原包存储对象、条目/内容文件数量与总量、自动通过/警告/待人工复核数量、状态、失败/退回原因、接收人、复核人、交接备注及各阶段时间；新增 `am_archive_intake_package_validation` 保存 DA/T 70—2018 检测编码、四性类别、结果和说明；新增 `am_archive_intake_package_item` 保存包与正式档案条目 ID、电子文件数量的有序关联。固定记录使用 Jakarta Data，列表使用 `createdAt DESC, id DESC` 的键集分页。

替代方案是把处理状态放入通用任务表，但当前是同步业务处理且失败记录本身是领域凭据，复用任务平台会混淆业务记录与执行入口。

### 3. 分离接收记录事务与全包处理事务

Controller 将 multipart 流复制到请求期临时文件，避免把 50 MiB 包整体常驻堆内存。`ArchiveIntakePackageService` 负责上传编排；独立记录 Service 在 `REQUIRES_NEW` 事务内通过 `StorageObjectService` 保存原始 ZIP 并创建 `RECEIVED`，因此后续失败仍保留原包。解析器完成标准结构和可自动执行的四性检测后，记录 Service 独立保存包编码、解析数量和检测报告。

上传请求只执行原包保存和自动检测：状态从 `RECEIVED` 进入 `CHECKING`，阻断检测失败时进入 `FAILED`，自动检测通过时进入 `PENDING_REVIEW`，不创建档案条目。接收人员可将其 `REJECTED` 并记录退回原因，或提交人工复核与线下交接确认。

确认接收时，系统从长期保存的原包重新解析以防请求期临时文件成为事实源，在一个事务内将状态改为 `ACCEPTING`，逐条调用档案核心 `ArchiveItemCommandService`，再通过 `ArchiveItemElectronicFileService` 保存内容数据和档案元数据 XML，最后写包关联并改为 `ACCEPTED`。处理抛错时数据库整体回滚；对象存储沿用 `StorageObjectService` 的事务回滚补偿删除已上传文件，状态恢复为 `PENDING_REVIEW` 并保存失败原因，允许排障后重新确认。

档案核心公开窄查询以按分类编码解析分类、按系统库角色解析启用库、按名称解析启用的密级和保管期限；目录文件中的责任者、题名、日期、页数、备注仅在目标分类存在同名动态字段时映射。每个条目继续经过现有 `archive:item:create` 权限、全宗/分类范围、动态字段、唯一约束和运行时规则。

档案和案卷不再维护 `electronicStatus`。repository role 是唯一生命周期真相源：`INTAKE` 中的条目是预归档档案，`HOLDING` 中的条目是正式档案，`TRANSFER` 中的条目处于移交阶段。正式档案没有 `DRAFT` 状态，借阅等业务状态也不得混入档案生命周期字段。离线标准移交信息包完成检测、人工复核和交接确认后直接在系统 `HOLDING` 库生成正式档案，不先写入 `INTAKE`，也不再写入 `ARCHIVED`。包内数据不能覆盖目标 repository role。

替代方案是在接收 Service 直接调用 Mapper 批量插入，但会绕过档案核心业务不变量和审计，故不采用。

### 4. 自动检测通过不等于正式接收合格

DA/T 70—2018 的移交接收检测中，目录结构、XML 可解析性、字段完整性、档号/内容关联、数量和字节数、压缩与加密状态可由本系统自动检测。来源固化信息、电子签名/印章/时间戳、内容人工打开浏览、杀毒软件、离线载体外观和读取速度依赖包外证据、可信服务、杀毒引擎或实物载体，本系统记录为 `MANUAL_REVIEW`，不伪造通过结论。

自动检测通过只进入 `PENDING_REVIEW`。接收人员必须确认来源固化信息、内容可读性、病毒检测、离线载体安全和《电子档案移交接收登记表》等交接手续，系统才允许进入 `ACCEPTING` 并最终 `ACCEPTED`。确认动作保存复核人、时间和交接备注，不能由上传动作隐式代替。

### 5. API 以包资源表达，同步返回最终状态

- `POST /api/v1/archive-intake-packages` 使用 multipart 字段 `file` 创建包资源，返回 `201` 和自动检测后的 `PENDING_REVIEW` 或 `FAILED` 包详情。
- `GET /api/v1/archive-intake-packages` 使用统一 `limit`/`cursor`，只返回当前用户的接收记录。
- `GET /api/v1/archive-intake-packages/{id}` 只返回当前用户的包详情和生成条目。
- `POST /api/v1/archive-intake-packages/{id}:accept` 接收人工复核与交接确认，确认后直接入系统 `HOLDING` 库。
- `POST /api/v1/archive-intake-packages/{id}:reject` 保存退回原因并终止该包接收。
- `POST /api/v1/archive-intake-packages/{id}:createDownloadLink` 为当前用户创建十分钟原包下载短链。
- `GET /api/v1/intake` 保留兼容，改为说明本地信息包已可用、外部连接仍未配置。

自动检测失败返回 `201` 的 `FAILED` 资源，而不是把已成功创建的接收记录伪装成 HTTP 请求失败。未认证、权限不足、文件缺失或超过上传边界发生在创建资源前，继续使用统一 ProblemDetail。

### 6. 前端采用单页工作台

页面首部是标准上传控件和 DA/T 93—2022 格式摘要，下方直接展示接收历史表。上传时禁用重复提交；列表覆盖骨架加载、错误重试和空状态；失败/退回原因在表格中可读。`PENDING_REVIEW` 详情提供四性检测结果、人工复核清单、确认接收和退回动作；`ACCEPTED` 可展开正式档案条目 ID、档号、分类和电子文件数量；所有详情可下载原包。界面复用 Element Plus 默认组件和现有页面间距，不新增装饰视觉。

## Risks / Trade-offs

- [原包成功但接收记录失败] → 原包存储和接收记录共用 `REQUIRES_NEW` 数据库事务；数据库回滚触发对象存储补偿删除。
- [载荷上传后数据库处理失败] → 所有载荷上传发生在同一处理事务，复用存储回滚补偿；补偿删除自身失败会记录结构化错误日志，后续由对象存储巡检清理孤儿对象。
- [同步处理耗时随条目和载荷增长] → 限制每包最多 100 条、500 个载荷及压缩/解压大小；超过交互预算后再演进为业务任务，而非本期提前引入。
- [档案核心某条校验失败时错误信息过长或泄露实现细节] → 只保存面向业务的异常消息并限制字段长度，未知异常统一为“信息包处理失败”。
- [自动检测或验收入库时进程崩溃会留下 `RECEIVED`、`CHECKING` 或 `ACCEPTING`] → 原包已保存可用于排障和恢复；本期不增加自动重试，后续按真实运行数据增加超时失败或人工重放。
- [标准只规定分类层次而未规定本系统分类 ID] → 明确约定全宗目录下第一层为系统分类编码，其余层保持为分类路径；找不到唯一分类或档号目录时拒绝。
- [门类元数据方案不同] → 通用配置只校验元数据 XML 可安全解析并保存原文；文书类按 DA/T 46—2009 的进一步字段级检测需要门类检测配置，不把通用结果宣称为全门类合规。
- [杀毒、签名和实物载体检测缺少基础设施] → 结果明确标记 `MANUAL_REVIEW`，只有接收人员依据外部检测证据逐项确认后才能正式接收。

## Migration Plan

1. Flyway 新增接收包和条目关联表，不迁移旧数据。
2. 部署后旧概览接口保持 URL 与既有字段兼容，只更新状态和文案；新页面开始调用包资源 API。
3. 回滚应用时新表可保留且不影响旧应用；若确认无需数据，可在独立后续迁移删除，不在回滚脚本中破坏接收凭据。

## Open Questions

无。DA/T 48 EEP、门类专用元数据检测配置、可信签名验签、杀毒适配器、实物载体登记与检测、跨人员监管和异步恢复均需独立业务合同。
