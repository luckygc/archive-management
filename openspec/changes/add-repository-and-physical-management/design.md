## Context

档案条目与案卷当前分别保存在 `am_archive_item` 和 `am_archive_volume`，固定字段之外的 `PHYSICAL` 字段按分类进入动态表。该模型能保存分类差异字段，但无法稳定表达档案当前属于哪个业务库、是否存在实物载体、实物当前位置及位置变更历史。

本设计需要同时服务预归档、室藏、业务部门实物移交和后续借阅场景。档案业务库只表达记录阶段；业务部门向档案室转交实物及保管责任由独立移交批次表达。固定资源继续使用 Jakarta Data；正式档案复杂搜索继续由 MyBatis 负责。HTTP 边界遵循 `api-contract`。

## Goals / Non-Goals

**Goals:**

- 用档案主表的单一 `repository_id` 表达业务库归属，避免组合多个流程状态判断记录可见性。
- 用独立实物对象表达条目或案卷是否存在实物，以及通用实物属性。
- 用层级位置和追加式历史表达实物当前存放位置及变更轨迹。
- 保持档案 ID 在预归档进入室藏以及实物移交接收前后稳定不变。
- 建立业务部门向档案室整批提交、接收或退回实物的最小闭环。

**Non-Goals:**

- 不实现实物移交审批、部分接收、跨馆移交、借阅或出库单据。
- 不改变案卷、条目分表模型，不支持任意层级嵌套。
- 不支持同一档案对象对应多个实物对象，也不建模可移动箱盒容器。
- 不迁移或删除现有分类 `PHYSICAL` 动态表。
- 不新增 PC 页面。

## Decisions

### 1. 业务库使用固定实体和少量稳定角色

新增 `am_archive_repository`，保存 `code`、`name`、`repository_role`、`enabled`、`sort_order`、`system_flag` 及通用审计字段。角色首期仅为 `INTAKE`、`HOLDING`；可以新增任意业务库实例，但新增角色需要同步代码和规格。

档案条目与案卷增加非空 `repository_id`。创建接口允许指定业务库；为兼容现有调用，未指定时使用系统内置室藏库。正式档案列表和搜索只返回角色为 `HOLDING` 的业务库记录，读取指定 ID 的详情仍按现有权限和数据范围处理。

不采用 `TRANSFER` 业务库角色：业务部门移交的是实物及保管责任，正式档案可能已经在室藏库但实物尚未移交，把它移动到移交库会错误改变正式检索和统计。借阅同样不得混入档案业务库。另一个方案是用档案与库的多对多关系表示“同时在多个库”，但当前用例只需要一个当前记录阶段，多对多会模糊唯一真相源，因此不采用。

### 2. 库变更是显式动作并记录历史

条目和案卷分别提供 `:changeRepository` 动作。Service 在同一事务内校验目标库启用、更新主表当前库并写入 `am_archive_repository_change_history`。历史保存档案对象类型、对象 ID、来源库、目标库、业务类型、业务 ID、原因、操作人和操作时间。

库角色是档案记录处于预归档或正式室藏阶段的唯一真相源。跨角色只允许 `INTAKE` 进入 `HOLDING`；正式档案不得通过通用库变更动作退回预归档。同一角色的业务库实例之间仍可受控调整并保留历史。

替代方案是允许普通 `PATCH` 直接修改库字段。库变化具有隔离和审计语义，普通字段更新难以强制写历史，因此不采用。

### 3. 实物对象反向引用档案所有者并保存当前保管状态

新增 `am_archive_physical_object`，保存可空的 `archive_item_id`、`archive_volume_id`，以及条码、载体类型、数量、数量单位、完好状况、当前保管状态、当前位置、备注、逻辑删除、版本和通用审计字段。数据库约束恰好一个档案外键非空，并通过两个部分唯一索引保证首期每个条目或案卷至多一个未删除实物对象。新建实物对象默认为业务部门保管；已有实物对象迁移为档案室保管，以保持现有库位和管理语义。

档案主表不保存 `physical_object_id`。反向引用可以由数据库外键保证实物对象一定属于真实档案，并为未来放宽为一对多保留自然迁移路径；API 仍直接返回 `physicalObjectId`。不存在未删除实物对象即表示仅有电子档案，不另存 `hasPhysical` 布尔字段。

替代方案是在条目和案卷各存一个实物信息 ID。该方案无法在数据库内自然保证同一个实物对象只被一种所有者引用，删除与未来一对多扩展也更复杂，因此不采用。

### 4. 实物移交批次拥有交接状态和清单快照

新增 `am_archive_physical_transfer` 和 `am_archive_physical_transfer_item`。批次保存唯一移交编号、来源部门、`PENDING_RECEIPT`、`ACCEPTED` 或 `REJECTED` 状态、提交/接收/退回责任人与时间及说明；明细引用实物对象并快照条码、载体、数量、单位和完好情况，避免实物后续编辑改写交接证据。

创建批次时校验 1 至 500 个互不重复、可访问且由业务部门保管的实物对象，在同一事务内写入批次、明细并把实物改为待接收。接收或退回均为整批原子动作：接收将实物改为档案室保管，退回恢复为业务部门保管，完成后明细不再占用“活动移交”唯一约束。批次一旦完成不可再次处理，也不允许更新或删除交接流水。

替代方案是把接收人、时间和退回原因直接写入实物对象。该方案无法表达批次清单、一次交接包含多个实物以及重复退回后的历史，因此不采用。首期不做部分接收，避免同一批次同时维护多种终态；存在差异时整批退回并重新提交。

### 5. 固定实物属性与分类扩展属性分工

条码、载体类型、数量、数量单位、完好状况和当前位置进入固定实物对象表。现有 `PHYSICAL` 动态字段继续按档案 ID 保存，仅表达分类特有的实物扩展属性，不作为实物存在性或当前位置的真相源。

本次不把动态 `PHYSICAL` 表外键改为实物对象 ID，以避免跨全部分类动态表执行破坏性迁移。读取档案详情时，动态扩展字段保持现有合同；实物对象通过独立资源读取。

### 6. 档案业务库、实物保管与真实库房独立

新增 `am_archive_warehouse` 表达真实物理库房，新增 `am_archive_storage_location` 保存所属库房、父位置、编码、名称、位置类型、启用状态、排序和通用审计字段。Service 拒绝跨库房父子关系、自引用及形成环的修改。

实物对象保存 `current_location_id` 作为高频当前值。批量位置调整使用 `POST /api/v1/archive-physical-objects:batchAssignLocation`，在一个事务内逐个推进乐观锁并为每个实际变化写入 `am_archive_physical_location_history`。历史是追加式业务流水，不允许更新或删除。

档案业务库、实物保管状态和真实库房不存在从属关系，也不要求同步：档案可已进入室藏库但实物仍由业务部门保管；档案室接收实物后也可先处于待上架状态，直到另行关联真实位置。只有档案室保管的实物允许关联库位。

### 7. API 与权限边界

- 业务库、真实库房与位置配置复用 `archive:metadata:manage`。
- 实物对象维护和档案库变更复用档案读取/更新权限，并继续经过档案数据范围校验。
- 实物移交批次创建、接收和退回复用档案更新权限，详情复用档案读取权限；每个动作校验批次内全部档案的数据范围。
- 集合规模可控的配置资源使用 `CollectionResponse`；增长型位置历史首期仅按单一实物对象读取，按操作时间和 ID 倒序返回受限集合。
- 条目和案卷至多关联一个实物对象，分别通过嵌套的单资源路径直接返回；不存在时返回 `404 ProblemDetail`，不使用空集合表达缺失。
- 标准资源使用 `GET`、`POST`、`PATCH`、`DELETE`；库变更和批量位置关联使用 AIP-136 风格 custom method。
- 实物移交批次通过 `POST /api/v1/archive-physical-transfers` 创建、`GET /api/v1/archive-physical-transfers/{id}` 读取，并以 `:accept`、`:reject` custom method 完成接收或退回；首期不提供缺少安全数据范围查询合同的批次列表。

## Risks / Trade-offs

- [现有创建调用没有库字段] → 迁移内置一个室藏库，创建请求未指定时解析该库，保持兼容。
- [档案业务库、实物保管和真实库房被界面或报表混用] → 使用独立资源与字段命名，正式档案量、已接收实物量和已上架实物量分别统计。
- [首期一档一实物限制未来多载体] → 使用实物表反向外键和部分唯一索引；未来只需移除唯一索引，不改档案主表。
- [动态 `PHYSICAL` 与固定实物对象并存容易混淆] → 规格明确通用字段与分类扩展边界，API 独立暴露实物对象。
- [批量调整中单条失败导致部分成功] → 使用单事务全成全败，错误指出无效实物对象或位置。
- [同一实物并发进入多个移交批次] → 创建活动明细唯一索引并推进实物乐观锁，任一冲突使整批回滚。
- [已接收室藏档案被重复创建] → 移交明细引用既有实物对象，接收只改变实物保管状态，不创建或复制档案记录。

## Migration Plan

1. 新增系统预归档库和室藏库；为现有条目与案卷回填系统室藏库。
2. 增加非空当前业务库外键和正式查询所需索引。
3. 创建库变更历史、真实库房、存放位置、实物对象和位置历史表。
4. 对已部署环境把错误 `TRANSFER` 库中的档案回迁到系统室藏库并软删除该库；已有实物对象回填为档案室保管。
5. 创建实物移交批次和明细表，部署实体、Repository、Service、Controller 和状态约束。
6. 回滚应用时可保留新增表和字段；数据库结构回滚仅在确认没有新移交记录后执行。Flyway 迁移不提供自动 down 脚本。

## Open Questions

- 借阅只由借阅单据与实物保管/位置表达的具体状态机，留待借阅业务规格确定，不再新增档案业务库角色。
- 一个档案对应多个实物载体、箱盒容器和案卷位置向卷内条目的继承规则，留待实际用例进入后扩展。
