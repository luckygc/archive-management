## Why

当前档案主表无法直接表达记录属于预归档库或室藏库，实物信息又仅以分类动态字段保存，导致正式检索隔离、实物存在性、保管责任、存放位置和位置变更历史都缺少稳定业务模型。业务部门向档案室移交的是实物及其保管责任，不是把档案记录移动到另一个业务库；需要校准“业务库”和“实物移交接收”的边界。

## What Changes

- 新增可配置档案业务库，仅使用预归档和室藏两类稳定角色表达档案记录阶段。
- 档案条目与案卷保存当前业务库；正式档案查询默认只返回室藏库记录，库变更保持原档案 ID 不变。
- 新增独立实物对象表；条目或案卷存在未删除实物对象即表示存在实物档案，首期每个条目或案卷至多一个实物对象。
- 新增实物保管状态、实物移交批次和批次明细；业务部门提交后由档案室整批接收或退回，已入室藏的档案只更新实物保管信息。
- 新增独立真实库房、库房内层级存放位置，以及实物对象批量关联位置和不可覆盖的位置变更历史。
- 将现有 `PHYSICAL` 动态字段收敛为分类特有的实物扩展属性，不再承担实物存在性、通用数量、条码或当前位置。
- 提供业务库、存放位置、实物对象、库变更和实物移交接收的最小 HTTP API。

### 目标

- 用一个直观库字段支撑预归档与正式室藏记录隔离。
- 让条目和案卷以同一套实物对象、位置和历史模型表达实物管理。
- 明确档案业务库、实物保管责任与真实库房互不替代。
- 让业务部门向档案室提交实物清单，档案室能够确认接收或说明原因后整批退回。

### 非目标

- 本变更不实现实物移交审批、部分接收、跨馆移交、出库或借阅单据流程。
- 本变更不把案卷和条目合并成可任意嵌套的统一档案表。
- 本变更不实现一个档案对象对应多个独立实物载体，也不实现箱盒等可移动容器模型。
- 本变更不交付新的 PC 管理页面，仅建立后端业务与 API 闭环。

## Capabilities

### New Capabilities

- `archive-repository-management`: 定义业务库配置、档案当前业务库、库变更和正式检索隔离。
- `physical-archive-management`: 定义条目/案卷实物对象、实物保管状态、业务部门实物移交接收、层级存放位置、批量关联位置和变更历史。

### Modified Capabilities

- `archive-record-routing`: 条目和案卷主表增加当前业务库，并按业务库角色约束正式查询与库变更。
- `archive-metadata`: `PHYSICAL` 动态字段仅表达分类特有实物扩展属性，不再作为实物存在性和当前位置的真相源。

## Impact

- 受影响真相源：`openspec/specs/archive-record-routing/spec.md`、`openspec/specs/archive-metadata/spec.md`，以及新增两项业务规格。
- 数据库新增虚拟业务库、真实库房、实物对象、实物移交批次与明细、存放位置和位置历史表，并为 `am_archive_item`、`am_archive_volume` 增加当前业务库外键。
- 后端新增 `module.archive.library` 与 `module.archive.physical` 子域的固定实体、Jakarta Data Repository、Service、Controller 和测试。
- 档案条目与案卷创建、读取、正式查询及库变更接口需要同步当前业务库合同。
- 不新增第三方依赖；复用现有认证、权限、审计和 ProblemDetail 错误机制。
