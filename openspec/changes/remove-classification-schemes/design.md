## Context

当前数据库通过 `am_archive_classification_scheme` 和 `am_archive_category.scheme_id` 将全局分类树分组，分类页面也要求先选择方案。但全宗真正保存的是 `am_archive_fonds_category_scope(fonds_code, category_id)`，分类字段、动态表、明细表、布局和规则都直接归属于分类。稳定 `archive-metadata` 规格已经把分类定义为不单独维护门类或分类分组的全局多层级结构，分类方案因此与现有业务模型重复。

当前分类方案还承担两项隐式默认行为：系统初始化默认方案；全宗未配置分类范围时返回默认方案下的分类。全宗分类关系另有 `default_flag`。用户已明确系统不需要任何默认分类，所有全宗都应显式勾选可用分类。

项目处于 `0.0.1` 未发布目标结构阶段，数据库结构通过基础 Flyway 和空库测试维护，不为未发布模型保留兼容表或双读分支。

## Goals / Non-Goals

**Goals:**

- 形成不带方案分组的全局分类树。
- 全宗只保存显式勾选的可用分类及排序，空集合语义稳定为“没有可用分类”。
- 删除分类方案和全宗默认分类的数据库、API 与页面概念。
- 在档案条目、案卷和导入的服务端写入边界校验全宗与分类关系。
- 保持分类字段、动态表、数据范围和历史档案读取边界不变。

**Non-Goals:**

- 不新增分类标签、分组、模板复制、继承或版本机制。
- 不把全宗编码写入分类或字段模板。
- 不因全宗取消勾选分类而删除现有档案、案卷或动态数据。
- 不把全宗可用分类关系替代成功能权限或档案数据范围。

## Decisions

### 1. 分类使用单棵全局树

删除 `am_archive_classification_scheme`，并从 `am_archive_category`、实体、请求响应和前端类型中删除 `scheme_id/schemeId`。分类父子关系只校验父级存在、未删除、不是自身或子孙；分类编码继续全局永久唯一。

替代方案是保留单一固定方案并隐藏页面入口，但这仍会留下无业务含义的表、外键、DTO 和默认状态，不能真正降低维护成本。

### 2. 全宗分类范围只保存显式集合和排序

`am_archive_fonds_category_scope` 保留 `fonds_code`、`category_id` 和 `sort_order`，删除 `default_flag` 及对应唯一索引。保存空数组会清空关系；按全宗查询可用分类时直接返回空数组，不回退全部分类或任何默认集合。

替代方案是空范围等于全部启用分类，但新增分类会被静默开放给所有未配置全宗，违背显式配置和失败关闭原则。

### 3. 写入边界统一校验显式关系

`ArchiveCategoryService` 提供窄的“校验全宗可用分类”业务方法，以全宗编码和分类 ID 查询固定关系。档案条目创建/更新、案卷创建和导入预检在业务副作用前调用；正常条目 Service 在导入提交时再次校验，防止预检与提交之间关系变化。

校验失败返回字段级 `ProblemDetail`，错误定位到 `categoryId`，并说明“该全宗未配置此分类”。现有档案查询和详情读取不应用该关系，避免取消勾选后隐藏历史数据；后续写入必须重新勾选分类后才能继续。

替代方案是只依赖前端分类下拉框过滤，但 API 调用和并发配置变化可以绕过客户端状态，不满足服务端边界要求。

### 4. API 直接删除未发布资源

删除分类方案集合及成员 API，不增加兼容端点。档案分类请求与响应删除 `schemeId`；全宗分类范围请求与响应删除 `defaultFlag`。其余 URL 和集合响应保持现有 `api-contract`。

前端分类页面移除方案选择器和方案标签，分类树直接展示所有分类；全宗可用分类弹窗移除默认复选框，保留分类选择、排序、添加和删除操作。

## Risks / Trade-offs

- [已有本地数据库仍包含旧结构] → 当前版本直接重写基础 Flyway；开发者需要按现有未发布版本口径重建本地数据库，不提供双结构兼容。
- [全宗清空分类后业务人员无法继续写入] → 保存允许成功并明确表达“没有可用分类”；写入返回可定位错误，重新勾选即可恢复。
- [取消勾选后历史档案仍可查询但不能修改] → 明确区分历史读取与当前写入资格，不删除、不隐藏数据，恢复关系后可继续修改。
- [导入预检后分类范围被并发修改] → 提交复用正常条目 Service 再次校验，整个批次异常时回滚。
- [删除方案后分类树较长] → 当前分类规模可由树形控件直接承载；不预先新增搜索、虚拟滚动或替代分组。

## Migration Plan

1. 直接重写基础 Flyway，删除分类方案表和两个默认字段，示例分类直接写入全局分类表，并为示例全宗显式写入分类范围。
2. 删除后端分类方案实体、Repository、Service 分支和 API；收敛分类及全宗范围 DTO。
3. 增加全宗分类写入校验并接入条目、案卷和导入路径。
4. 删除前端分类方案 client/type/UI，简化全宗分类弹窗及测试。
5. 更新稳定文档与 change delta，执行格式、后端、前端和治理验证。

回滚仅适用于未发布代码：回退本 change 并重建空库。若未来已有正式数据库上线，不得直接复用本迁移策略，必须另建增量迁移并先把现有默认方案分类显式展开为全宗分类关系。

## Open Questions

无。用户已确认不存在默认分类，空范围按没有可用分类处理。
